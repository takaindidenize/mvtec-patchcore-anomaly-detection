# Decisions

One line per task: what was decided, and why.

- **Setup:** The project lives outside OneDrive at `C:\dev\mvtec-ad`, because syncing a 4.9 GB dataset of thousands of small image files slows I/O and can lock files during training.
- **Setup:** Python is pinned to 3.12 rather than the 3.11 fixed in AGENTS.md section 3, because 3.11 was not installed and every dependency in section 4 supports 3.12; the Dockerfile will use `python:3.12-slim` so development and production stay on the same interpreter (approved by the user).
- **Setup:** Threshold calibration moves ahead of T4 and every test metric is produced by a single unlock run after T7, because the T4-T7 definitions of done required test metrics that section 16 and rule 1 forbid before the design is frozen (approved by the user).
- **Setup:** `bottle` is the only category until the full pipeline works end to end, because each additional category costs nine CPU runs and adds no new code path (approved by the user).
- **T0:** torch and torchvision are installed from the PyTorch CPU wheel index in both the Makefile and CI, because the default PyPI wheels bundle CUDA on Linux and would alone exceed the 2 GB image budget of T11.
- **T0:** Ruff is restricted to Python files via `include`, because it otherwise reformats the Python snippets embedded in `AGENTS.md`, and the contract document must not be rewritten by a formatter.
- **T1:** The split is a pure function over a list of paths, tested without the dataset, while the dataset-backed tests carry a skip marker, because CI never has the data yet determinism and disjointness still have to be proven there; the seed sweep of section 10 is driven by a `load_config(..., seed=)` override rather than a new config key, since the section 11 schema is declared complete.
- **T2:** The audit checks mask binarity and image/mask size agreement on top of the counts and pairing that section 5 asks for, because a non-binary or misaligned mask would corrupt every pixel metric without raising an error; all 15 categories came back clean, so the pairing rule the dataset code relies on is now verified rather than assumed.
- **T3:** AU-PRO draws its thresholds from the clean-pixel quantiles *and* a linear span of the score range, then keeps the best overlap at each false positive rate, because a perfect predictor collapses the clean scores onto a single value and a quantile-only grid would score that case zero instead of one; threshold calibration ships alongside the metrics since it reads only `val_normal` and must exist before any model is fitted.
- **T4:** The Mahalanobis baseline pools the deepest backbone stage (`layer4`, stride 32, 2048-d) and estimates the covariance with Ledoit-Wolf shrinkage, because the spec was silent on both and ~167 training images against 2048 dimensions make the raw covariance singular; Ledoit-Wolf has no tuned parameter and sees training data only (approved by the user).
- **T4:** The section 12 bundle gains a `model_state` key holding model-specific weights and statistics, because Mahalanobis statistics and autoencoder weights had no home and serving must load one file only (approved by the user).
- **T5:** The autoencoder is a five-stage stride-2 convolutional network with a 128x7x7 bottleneck, trained with Adam (lr 1e-3, 50 epochs, MSE) whose hyperparameters are named constants in code rather than config keys, because the section 11 schema is complete; its image score is the maximum of the per-pixel error map, chosen to match PatchCore's score definition, and none of these values were tuned on test data (approved by the user, except the max-score choice, which the spec left open).
- **T6:** PatchCore follows the spec order exactly (fuse the upsampled `layer3` map with `layer2`, then 3x3 average-pool) and runs the greedy k-center search on the full 1536-d patches without random projection, because section 8.1 lists neither a projection nor a per-layer pooling step; the search starts from a point drawn with the config seed, so two runs with the same seed give an identical memory bank.
- **T7:** The coreset ratio stays at the config default of 0.01, because in `results/coreset.md` the 0.001 bank covers held-out normal images clearly worse than 0.01 (a much higher `val_normal` median score), while 0.1 improves that coverage only modestly for roughly ten times the memory, several times the fit time and about twice the query latency; the choice rests on `train_fit` and `val_normal` measurements alone and no test image was read.
- **T8:** The design was frozen at the T8 runner commit and `src/run_eval.py` opened the test split exactly once for 3 models x 3 seeds, applying each bundle's `val_normal`-calibrated threshold unchanged; `results/metrics.md` refuses to be overwritten so a second run cannot happen by accident, and every figure is reported as measured, including the autoencoder's low recall at its calibrated threshold and the near-chance localization of the image-level Mahalanobis baseline.
- **Setup:** `httpx` joins the development dependencies, because FastAPI's `TestClient`, which T9 requires, depends on it; it is test-only and never imported by the serving path (approved by the user).
- **T9:** The service loads the bundle named by `$MODEL_ARTIFACT` once in the app lifespan and takes every preprocessing value from it, `/info` omits `model_state` as well as `memory_bank` because it is bulky and not JSON-serializable, and the heatmap puts the calibrated threshold at the middle of the colour scale so a colour means the same for every image; a missing or corrupt artifact leaves the app running and answering 503 instead of crashing at startup.
- **T10:** The benchmark drives the real FastAPI app with 200 sequential single-image requests per model after a warm-up and reports both the client round trip and the service's own `latency_ms`, using `val_normal` images so the test split stays out of it; the app also runs one throwaway prediction at startup, because the first request after startup was an order of magnitude slower than steady state.
